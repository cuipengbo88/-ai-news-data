2. 把这个"接口报错"当成产品原型的教材：错误处理才是 vivo coding 的分水岭

你业余在做 vibe coding 的原型，今天这份原始数据简直是送上门的教材。{"error":"blocked","code":567} 这种结构化返回，本质上是一个设计良好的 API 该有的样子：有错误态、有错误码、有 requestId、有自助恢复入口。对比一下很多人在原型阶段写的接口——出错直接返回空数组、或者抛一个没人看得懂的堆栈，前端拿到就是一屏白。

我的判断是：vibe coding 的成败，八成不在功能跑通那一刻，而在出错那一刻的体验。功能跑通是最容易的，AI 帮你生成一次就能跑。但用户真正放弃一个产品，往往是在它出错的时候：加载失败没有任何提示、点了按钮没反应、数据为空分不清是"没有"还是"坏了"。今天这个 567 恰好给了你一个可复用的范式。

具体怎么用？第一，给你的原型接口定义一个统一的返回壳：成功走 data，失败走 error + code + help 三件套。code 用来让程序分支处理，help 用来让人自救，这两者服务的是完全不同的对象，缺一不可。有了 help 字段，你连客服成本都省了——用户自己点进去就能解决，不用来问你。第二，前端要区分"空态"和"错态"。空态说"这里暂时没有内容"，错态说"加载失败，点此重试"。这两个文案今天就去改，改完用户留存会有肉眼可见的差别。

第三，也是最容易被忽略的一点：requestId 这类追踪字段。你现在是一个人在做原型，觉得用不上；但只要你的原型打算给客户试用哪怕三个人，你就需要它。用户截图给你说"报错了"，你让他把 requestId 发过来，就能在日志里定位到那一次请求。没有它，排查一个偶发错误平均要花 1 小时以上；有了它，通常 5 分钟搞定。

再往上一层，这个案例其实在教你如何设计"降级"路径。一个成熟产品在数据源被拦截时，不该是页面空白，而应该是：展示上一次的缓存结果 + 一行小字提示"数据更新于昨天"。用户看到的是"稍旧但可用"，而不是"坏了"。你现在给客户做的很多小工具都是这个逻辑——比如给实体店做的排队叫号、会员积分、预约排期，后台接口一抖，前台就不能停摆。凡是线下场景在用的工具，缓存和降级不是优化项，是及格线。

最后给一个今天就能做的练习：拿你现在手上任意一个原型，问自己三个问题——数据源挂了它会显示什么？用户看到错误后知道下一步该做什么吗？你能在五分钟内定位到是哪一次请求出的问题？三个问题里有两个答不上来，就先别加新功能，先把这三个补上。这是从"能跑的玩具"跨到"能交付的产品"最便宜的一步，也是大多数原型死掉的地方。

🛠️ Vibe Coding 可玩的

统一返回壳：data / error / code / help 四件套

今天就能改：给你的原型所有接口定一个返回格式。成功走 data，失败走 error 文案、code 分支码、help 自救链接。四件套设计好，前端写分支逻辑会非常省心，也方便以后接第 N 个数据源。

空态 vs 错态：两个 UI 文案的区分

这是最便宜的体验提升。空态写"这里暂时没有内容，去看看别的"，错态写"加载失败，点此重试"。绝大多数原型把这两个混成一个"暂无数据"，用户分不清是产品没做完还是真的没东西。改完当天就能感受到差别。

缓存兜底 + 时间戳提示

数据源挂了不要白屏。把你上一次成功拿到的结果存进 localStorage 或本地文件，下次源失败就展示缓存，并在角落写一行"数据更新于 X 日 X 时"。线下在用的工具尤其需要这套，因为门店不接受"系统坏了请稍等"。

requestId 日志链路

每次请求生成一个随机 ID，前端报错时一并展示、后端日志一并记录。给客户试用之前一定要加，用户截图你就能定位。一个人做原型也建议加，因为偶发问题最耗时间，而偶发问题恰恰是 AI 最难帮你复现的。
